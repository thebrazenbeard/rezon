# Rezon v0.1 General Multi-Node Solver Spec

## Status

Approved direction from Patrick for Rezon:

- Rezon is a runnable reasoning framework from the beginning, not only a research archive.
- The first executable demo is a **general multi-node reasoning problem solver**.
- The first runtime remains provider-agnostic and must run with deterministic/mock workers.
- No external model provider, Ultra path, graph database, distributed service, persistent identity tracker, or Vera runtime integration is required for v0.1.

This spec narrows the existing `docs/EXECUTABLE_FRAMEWORK_DIRECTION.md` and `ROADMAP.md` into one executable milestone.

## Goal

Build the smallest trustworthy runtime that can accept a task, preserve the literal proposition, decompose the task into explicit reasoning work, execute multiple independent deterministic nodes, run an opposition pass, reconcile claims and conflicts, verify evidence coverage, integrate the surviving result, and emit a machine-readable receipt explaining what happened.

The purpose of v0.1 is to prove the **reasoning fabric** before adding model-provider complexity.

## Core principles

1. **Literal proposition first.** The task's request, referent, scope, qualifiers, and constraints survive decomposition unchanged.
2. **Typed reasoning products.** Workers emit claims, evidence references, assumptions, unresolved items, and execution metadata rather than free-form prose alone.
3. **Multi-node does not mean fake consensus.** Duplicate claims do not become more true because several nodes repeat them.
4. **Opposition is structural.** A dedicated node tries to falsify the current leading candidate without silently rewriting the task.
5. **Evidence is required for accepted factual claims.** Unsupported claims may remain unresolved but cannot be silently promoted.
6. **Conflicts remain visible.** The integrator does not erase incompatible supported claims.
7. **Determinism first.** The mock runtime must produce stable results and stable receipt ordering for the same inputs.
8. **Failure is typed.** Expected states include `UNAVAILABLE`, `INSUFFICIENT_EVIDENCE`, `CONFLICT`, `INVALID_TASK`, `WORKER_FAILED`, and `RESOURCE_LIMIT` rather than one generic exception surface.
9. **Execution state is not effect state.** A completed Rezon reasoning run proves only that the local runtime ran; it does not imply deployment, provider activation, identity promotion, or external effect.

## v0.1 architecture

```text
TaskEnvelope
  -> PropositionTyper
  -> Decomposer
  -> PlanGraph
  -> NodeExecutor
       -> deterministic reasoning nodes
       -> independent cross-check node(s)
  -> OppositionNode
  -> EvidenceVerifier
  -> Reconciler
  -> Integrator
  -> ResultReceipt
```

### TaskEnvelope

Required fields:

```python
@dataclass(frozen=True)
class TaskEnvelope:
    task_id: str
    literal_request: str
    constraints: tuple[str, ...] = ()
    context_refs: tuple[str, ...] = ()
    resource_budget: int | None = None
```

v0.1 does not add authority, privacy, or persistent-subject semantics beyond carrying opaque context identifiers. Those remain later framework concerns.

### Proposition

```python
@dataclass(frozen=True)
class Proposition:
    proposition_id: str
    text: str
    proposition_type: str
    referent: str | None
    scope: str | None
    status: str = "UNPROVEN"
```

For the first deterministic runtime, proposition typing may be deliberately conservative. Unknown types are allowed; rewriting the literal request is not.

### EvidenceItem

```python
@dataclass(frozen=True)
class EvidenceItem:
    evidence_id: str
    source_ref: str
    content: object
    version: str
```

The demo uses an in-memory evidence store. Every worker receives explicit evidence items; no hidden global evidence is allowed.

### Claim

```python
@dataclass(frozen=True)
class Claim:
    claim_id: str
    proposition_id: str
    text: str
    value: object
    evidence_refs: tuple[str, ...]
    assumptions: tuple[str, ...] = ()
    status: str = "PROPOSED"
```

### ReasoningNode protocol

```python
class ReasoningNode(Protocol):
    node_id: str
    operator_type: str
    independent_group: str | None

    def run(self, task: TaskEnvelope, proposition: Proposition,
            evidence: tuple[EvidenceItem, ...]) -> "NodeResult": ...
```

### NodeResult

```python
@dataclass(frozen=True)
class NodeResult:
    node_id: str
    claims: tuple[Claim, ...]
    unresolved: tuple[str, ...]
    error_state: str | None
    execution_receipt: "WorkerRunReceipt"
```

### PlanGraph

The planner emits explicit node invocations and dependencies. v0.1 supports:

- independent nodes that can run concurrently;
- dependent nodes that wait for predecessors;
- opposition and verification stages after primary candidate generation.

The executor must reject dependency cycles.

## First executable demo

The built-in demo is a generic constraint-selection problem, not a domain-specific assistant feature.

Input evidence defines several candidates with attributes plus explicit constraints. Example shape:

```text
Candidates:
A: cost=8, latency=5, reliability=0.91
B: cost=6, latency=7, reliability=0.97
C: cost=9, latency=4, reliability=0.99

Constraints:
cost <= 8
latency <= 7
reliability >= 0.95
```

The correct surviving candidate is B.

The plan uses genuinely different deterministic operators:

1. `constraint_filter` eliminates candidates that violate explicit constraints.
2. `independent_checker` recomputes feasibility from the raw evidence without seeing the first worker's claim.
3. `opposition` tries to produce a concrete counterexample showing the leading candidate violates a constraint.
4. `evidence_verifier` rejects any accepted claim whose referenced evidence is missing or version-mismatched.
5. `integrator` returns a result only when the surviving candidate is supported and unrefuted.

This demo proves the runtime can coordinate several reasoning nodes. It does **not** prove natural-language reasoning quality or LLM capability.

## Reconciliation rules

For v0.1:

- Same value + same upstream evidence is corroboration, not independent evidence multiplication.
- Same value + independently recomputed path may be recorded as independent agreement, but evidence identity remains visible.
- Supported incompatible values produce `CONFLICT` unless the opposition/verifier invalidates one side.
- Missing evidence produces `INSUFFICIENT_EVIDENCE`.
- Worker failure does not count as a vote for or against a candidate.
- The integrator must never convert absence of a result into consensus.

## ResultReceipt

The final result is accompanied by a deterministic JSON-serializable receipt:

```python
@dataclass(frozen=True)
class ResultReceipt:
    task_id: str
    plan_id: str
    proposition_id: str
    worker_runs: tuple[WorkerRunReceipt, ...]
    accepted_claim_ids: tuple[str, ...]
    rejected_claim_ids: tuple[str, ...]
    conflicts: tuple[str, ...]
    unresolved: tuple[str, ...]
    final_status: str
    final_value: object | None
```

Stable sorting is required so identical inputs produce byte-stable JSON after canonical serialization.

## Hostile acceptance cases

v0.1 is not complete until tests demonstrate all of the following:

- the literal request survives decomposition unchanged;
- a worker that rewrites the proposition cannot silently replace the task;
- duplicate claims from correlated workers do not create synthetic consensus;
- a worker with a missing evidence reference cannot produce an accepted factual claim;
- two supported incompatible answers yield `CONFLICT`;
- an opposition node that finds a real counterexample blocks the candidate;
- an opposition node that finds no counterexample does not invent one;
- one worker failure does not erase successful independent work;
- a cyclic plan is rejected;
- repeated runs on identical deterministic inputs yield identical canonical receipt bytes;
- the receipt distinguishes `COMPLETED` from any external deployment/effect state.

## Technology constraints

- Python >= 3.11.
- Standard library for runtime implementation.
- `pytest` is the only required development/test dependency.
- No network access is required by the test suite.
- No database is required.
- No nondeterministic model calls are allowed in the core acceptance suite.

## Completion boundary

`REZON_V0_1_SOURCE_PASS` may be claimed only when the exact implementation commit passes the full test suite and hostile acceptance suite from a clean checkout.

That status means source implementation and tests passed. It does not mean merged, packaged, published, deployed, provider-connected, Vera-integrated, or production-qualified.
